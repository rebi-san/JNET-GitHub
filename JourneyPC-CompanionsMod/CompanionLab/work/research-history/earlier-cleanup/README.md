Background-paused clients do not advance; receive age does not measure time spent in the kernel socket backlog.

The UDP implementation uses Winsock and Windows BCrypt HMAC-SHA256 with a random 256-bit invite key and 128-bit process identity. It binds only 127.0.0.1, has no unauthenticated control listener, caps parsing at 32 attempts/second and drains at most four datagrams per game update. The helper passes the invite through the checked loaded-DLL configuration export; it never writes it to normal logs. Copy Invite explicitly uses the clipboard, which other local applications may observe; the helper does not automatically clear it. There is no encryption, relay, external service or public-IP privacy guarantee. Journey's native Steam traffic is unchanged.

## Proposed architecture and privacy boundary

For Milestone B, the smallest plausible architecture is a narrow in-game native adapter plus Lua diagnostics. Native access appears necessary because exposed script logic does not implement connection allocation, remote ownership or receive routing. This is a working hypothesis, not a demonstrated impossibility of Lua-only implementation. Reuse existing movement/animation/event synchronization only after its ownership and message formats are understood. A launcher or relay cannot by itself make `GetRemoteDude` represent two peers.

The future adapter should keep a bounded mapping from authenticated room participant ID to remote entity, per-peer synchronization context and chapter/session epoch. Disconnect must remove that participant's references; reconnection must create a new epoch so delayed packets cannot revive stale entities. The correct authority model remains undecided pending native tracing. Do not copy one connection's state through the same remote slot or treat lobby members as owners without authentication.

Design that mapping as a collection of companion records, not named second/third-player fields. Each record needs independent native ownership, synchronization state and cleanup; identities must remain separate from reusable allocation slots. Iterate the bounded admitted collection for updates and chapter handling. Build-specific offsets and the current single-trial diagnostics belong in the native adapter/probe, not the future membership model. Before choosing transport topology, measure per-participant update size/rate and aggregate bandwidth, CPU, draw and cloth costs; sixteen participants must not implicitly require fifteen independent copies of every expensive subsystem or an unexamined all-to-all connection topology. These are design constraints, not a decision to add a server or rewrite vanilla synchronization now.

Scarfhelper is diagnostic only; no group-session helper, service, membership protocol or private mode is implemented. No online service was contacted or deployed. For the initial controlled baseline, assume vanilla networking can expose endpoints to peers. It is not an IP-hiding mode.

The supplied Steam header `include/steam/isteamnetworking.h:175–180` describes `AllowP2PPacketRelay` as allowing fallback when direct/NAT-traversal connections fail, not forcing relay-only traffic. Its socket state enum includes remote candidate exchange, and `P2PSessionState_t` contains remote IP/port fields. The executable contains `SteamNetworking005`; this does not establish which overload/path it actually calls. Neither that library nor a Steam storefront proves access to newer Steam Datagram Relay APIs or permission to operate another app's service. No free, terms-compliant hosted option has been verified; that requires checking the chosen provider's current official requirements before selection.

Deferred options for a future IP-hiding mode; evaluating or implementing these is not required for the current gameplay milestones:

| Option | Local evidence / requirement | Tradeoff |
| --- | --- | --- |
| Existing Steam transport | Present interface allows relay fallback; a proven relay-only path and permission are missing | Could reuse transport, but current evidence does not meet privacy requirements |
| Independent service using an established QUIC/TLS implementation | Requires an authorized host, maintained library, authenticated private rooms and a complete game transport adapter | No mandatory software fee need be assumed, but hosting/bandwidth are not guaranteed free; relay adds a path through its location |
| Small TLS-over-TCP relay for a later controlled test | Same adapter and authentication requirements, TLS from an established library | Simpler framing but loss can delay subsequent movement updates; only acceptable if measured gameplay stays faithful |

No specific external component is selected yet. A small relay must still enforce bounded authenticated membership, expiring high-entropy invitations, join rate limits, message type/length/version/participant ownership checks and resource caps. Remote input must remain data: do not reuse `Garnet.lua::ParseServerCommand` or `PWeb3.lua::RemoteFunHandler`, which expose command execution behavior. A helper should use authenticated local IPC, not an open control port.

If TLS terminates at a relay, its operator can read gameplay payloads and observe incoming public endpoints. End-to-end encryption would require a separate authenticated key design using established libraries; it is not provided by calling a relay encrypted. If a participant operates that relay, that participant can see connection endpoints. The gameplay host may be a room member without operating the infrastructure.

For a future mode advertised as hiding public IP addresses, acceptance requires intercepting/preventing original direct matchmaking, signaling, connection probes and reconnect paths before enabling a protected room, with no direct fallback. Startup, join, gameplay, reconnect, relay failure and shutdown must be captured locally at every participant including the gameplay host, for IPv4 and IPv6 where available. Inspect payload metadata as well as packet destinations. On relay failure, stop protected gameplay and show a connection error. Do not market endpoint privacy until those tests pass. These requirements are deferred and do not block ordinary prototype connectivity. Bandwidth should be measured from actual update sizes/rates; with naive relay fan-out, aggregate forwarded update traffic grows approximately with N(N−1).

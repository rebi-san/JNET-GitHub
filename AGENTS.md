# Workspace rules

- Create a bullet point plan before editing.
- Work inside this repository; ask before accessing or modifying files outside it.
- Make targeted changes, preserve unrelated work, and do not modify original Journey game files.
- Use the existing JNET build system. Building requested changes is authorized now and in future sessions without asking again.
- The user handles launching JNET/Journey and gameplay tests. Do not repeat this reminder in routine updates or completion messages.
- After a new package is built and verified, continue directly into the installation workflow rather than ending with a build-only report. Request installation approval once for all bottles applicable to the current test, then update and verify every approved bottle. If installation of the current build is already authorized, proceed without asking again. Group any required installation permission request across the target bottles instead of requesting permission separately for each bottle.
- Do not install dependencies, change system settings, use the network, or perform repository-changing Git operations without explicit authorization.
- Use the bottles established for the current test. The three approved participants are devishaz, rebishaz, and smooviepuffs; update all three for a three-player test, or the applicable subset for a narrower test.
- Report build results separately from live gameplay validation.
- After each successful, hash-verified installation, remove superseded release ZIPs, version-specific Python installer scripts, and routine build logs. Keep the current release ZIP, installer and log, the reusable installer entry point, installation receipts, and the latest rollback for each bottle. Preserve important research, useful experiments, their source and results, and unique troubleshooting evidence before removing any old artifacts; age alone does not make research or an experiment disposable.
